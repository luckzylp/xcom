# 对话框留在应用窗口内，装饰语义由应用自己拥有

波特率对话框与「关于 XCOM」都是应用窗口**内部**自绘的浮动对话框，不是独立的系统窗口。我们决定保持这个形态：不开多视口、不要原生装饰，代价是标题栏与关闭按钮的位置全部由应用自己实现——因此在 Linux 上要读桌面的 `button-layout`（`gsettings get org.gnome.desktop.wm.preferences button-layout`）来决定关闭按钮放左还是放右，而不是硬编码一个位置。

## Considered Options

- **改成独立的系统窗口（多视口 / 原生装饰）**：能白拿系统的按钮布局、拖动与缩放行为，但要多视口支持，还要把现有 UI 状态镜像到新窗口里，且各平台的原生行为差异都要重测。当前两个对话框都很小，成本与收益不成比例。
- **固定把关闭按钮放左侧**（GNOME 默认）：实现最省，但用户在 GNOME Tweaks 里把按钮改回右侧后就不跟随了，而这条需求的出发点恰恰是「跟随系统」。
- **通过 XDG Desktop Portal 的 `org.freedesktop.portal.Settings` 读设置**：在 Flatpak 沙盒里也能读到（`sctk-adwaita` 走的就是这条），但要新增 D-Bus 客户端依赖，而本应用目前不做沙盒分发。

## Consequences

- 只在 Linux 上探测；Windows / macOS 的关闭按钮固定在右侧，与本机原生习惯一致，也没有本机可验证的对照。
- 探测结果在进程内**读一次并缓存**，改了 GNOME 按钮布局需要重启应用才生效；这与既有的 `titlebar-font` 探测（`src/i18n.rs`）保持同一套做法。
- 读不到设置时（非 GNOME 桌面、没有 `gsettings`、key 缺失）退回右侧，也就是当前的行为。
- egui 0.36 的内建标题栏把关闭按钮硬编码在右侧且**没有镜像开关**，所以「关于 XCOM」也必须改用自绘标题栏；两个对话框共用同一个头部实现，否则同一应用里两个对话框的按钮位置会互相矛盾。
